## Route A — delegated PC usage of the implementation that exists

The parent delegates an authorized bounded operation to the connected PC task runtime. That local runtime executes the adapter and returns verified task data/links. This is a delegation route; the cloud parent does not acquire native RyanOS tools. Local MCP registration also does not guarantee that this particular delegated runtime reloads the configured tools; verify availability first. Where it does not, the local executor can explicitly start the reviewed `scripts/task-connector-mcp.mjs` process and speak its stdio protocol, as the synthetic end-to-end test did.

Exact setup, after separate migration/deploy/access approval:

1. Confirm the existing app host and database. Review/apply the optional task provenance column/index migration, then deploy the tested task API inside the existing app. Keep bearer access disabled initially.
2. Ryan signs into RyanOS. Use the authenticated `/api/auth/session` response and `/api/task-connector/catalog` to identify his owner ID and real owned Area/Project IDs; do not share his cookie/password.
3. Approve the owner's explicit Area allowlist, expiry and operations. Privately configure server `RYANOS_TASK_CONNECTOR_ENABLED`, `SHA256`, `OWNER_ID`, `DOMAIN_IDS`, `OPERATIONS`, and `EXPIRES_AT` settings as fully named in `TASK_CONNECTOR.md`. Start with read-only. The digest represents a separately approved high-entropy task-only token; no actual value is generated by this plan.
4. Privately supply `RYANOS_TASK_API_URL` and `RYANOS_TASK_CONNECTOR_TOKEN` to the PC task process environment. Verify that the selected execution environment actually receives them without printing their values. The adapter reads them internally; do not put the token in commands, chat or repository files.
5. On the PC, initialize the adapter, call catalog/list/read, confirm owner/Area isolation, and return read results to the parent. If local MCP registration is used, verify its five tools are callable in that local runtime. Their visibility there is no evidence of visibility in the cloud parent.
6. After separate real-write approval, enable `read,create,update` as appropriate. The parent delegates reviewed action batches; the PC resolves IDs, searches existing/closed work, binds source keys or creates missing actions, applies version-checked patches, reads back committed results and returns absolute task links. The parent reports saved only from that evidence.

This route requires the PC to be available. It is not unattended direct cloud integration, and it has not been activated.

## Route B - historical design, now implemented locally with activation pending

Use [the current activation report](REMOTE_TASK_MCP_ACTIVATION.md) for implemented endpoints and exact owner steps. The remaining text in this section records the earlier proposed design.

Proposed endpoint: **`https://<confirmed-existing-RyanOS-host>/api/mcp/tasks`**. If the handoff host is confirmed, the candidate is `https://daily-action-os.vercel.app/api/mcp/tasks`. **This route does not exist yet.** It would be a Node Next.js route in `command_center`, using standard Streamable HTTP MCP and the same five tools/service/contracts. It would use the existing app database/task models directly through that owned service, not a second store, public task API bypass, new website or PC tunnel.

A stateless transport is the smallest fit for the existing hosting: initialize/tool discovery/tool calls over POST, JSON responses and GET 405 when no SSE channel is supplied, authentication on every request, no in-memory cross-instance session dependency. Prefer the official TypeScript MCP SDK for this extension. Keep one shared tool contract so remote transport cannot loosen the existing field, owner, Area, provenance or version checks.

**OAuth is the remaining access component.** The existing NextAuth credentials session is human login, not an OAuth 2.1 authorization server for ChatGPT. The local task bearer credential also cannot be assumed to fit the cloud plugin's connection flow. Do not publish private tasks with `noauth`, reuse a session cookie as a token, or paste the local token into a plugin description.

Use an existing approved OAuth/OIDC provider if Ryan already has one meeting MCP requirements; none was identified in the reviewed app. If there is no such provider and no paid service is desired, an OAuth authorization-code/PKCE extension within the same RyanOS app is a separately reviewable authentication build. It can reuse Ryan's existing session for sign-in and an owner consent screen, but needs durable authorization code/token/grant records in the existing database. Those are access records, not another task store. That authorization server is **proposed, not implemented or production-approved**.

Required remote auth design:

- OAuth 2.1 authorization code with PKCE S256; exact approved client/redirect/resource validation and single-use expiring codes. Use CIMD/predefined approved client registration as supported by the parent's actual connector flow; do not guess its redirect URI or allow arbitrary redirects.
- Public protected-resource and authorization-server discovery metadata, a `WWW-Authenticate` challenge, and audience/resource binding to the canonical MCP endpoint. Metadata may be public; task tools/data may not.
- Scopes `tasks:read`, `tasks:create`, `tasks:update`; selected owned Area IDs and owner ID belong to a durable grant, not tool arguments. Read is required for writes. An access token resolves to `TaskAccess`; expiry, revocation, issuer/audience and scope are checked for every call. Keep task tokens separate from app cookies and runner credentials.
- Read-only consent first; write scopes require explicit Ryan consent/approval. Support owner revocation and a finite access lifetime. Any refresh-token/offline access option needs separate approval, rotation and revocation tests.
- CSRF protection for owner consent; deny foreign origins at the transport boundary; safe request size/error handling; no token/body logging. CCHCS scope is only for appropriate PHI-free operational task content.

Potential discovery paths and authorization/token/revoke paths would be defined during that build, using MCP/OAuth standards. They are not current RyanOS endpoints and must not be described as available APIs.

Exact connection/setup sequence after that code is reviewed and tested:

1. **First verify the cloud parent's account/workspace supports adding a private authenticated remote MCP/plugin connection.** The documented ChatGPT path is Developer mode (availability depends on policy), then Plugins → plus → server URL → create connection → review discovered tools. If unavailable, stop at delegated PC usage; do not provision a secret for an unusable connector.
2. Approve the remote transport/authentication extension and its narrow scopes. Implement/tests must cover missing/expired/revoked/wrong-audience tokens, PKCE/code replay, exact redirect checks, owner/Area isolation, read-only grants, write-scope consent, duplicate retries and stale/terminal updates.
3. Approve the associated schema changes and deployment on the existing RyanOS host. Approve any necessary private signing/credential material, OAuth client setup, redirect allowlist and grant issuance; none is created or altered during planning.
4. Add the **remote HTTPS MCP URL in the cloud parent environment**, using the supported private plugin/MCP connection UI. Copy its displayed exact OAuth client metadata/redirect information into the reviewed authorization configuration. Do not use local `.codex/config.toml` as a substitute.
5. Ryan completes the app sign-in/consent handback. Grant only task read and selected owned Areas. Confirm the five tools actually appear and catalog/list/read work **in the cloud parent's tool set**, not just on the PC.
6. Verify a denied out-of-scope read and a denied write under the read-only grant. After separate write consent and real-task authorization, perform one bounded create/read/update/readback and return its link from the cloud parent. Only then call direct parent integration ready.

No new paid service is assumed. Reusing the existing hosting may still require checking its present runtime/plan limits; this plan makes no hosting availability or cost guarantee. A remote connection can remove the PC dependency once actually implemented and connected.

## Concise product proposal for parent review

Preserve the time-blocking grid and placement data, the daily snapshot and saved daily context, and the existing daily/weekly review workflows. Simplify the supporting Tasks screen into short next-action rows filtered by the actual owned Rykas, AP Sports, CCHCS and Personal Areas. Default to Ready, Waiting/Blocked and Later views; open a row for responsibility, details, draft and source links. Keep advanced maintenance/history accessible. Start notes/photo/screenshot intake in conversation, flag ambiguity, and reconcile reviewed actions with the same source-key/version contract. The smallest next UI slice is compact `/tasks` creation/list/detail behavior; no core-screen redesign, OCR, scheduler or new inbox store.
